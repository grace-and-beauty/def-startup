# Підтримка закладів — процедура

_Для пілота: підтримку веде засновник. Адмін-панелі немає, є SQL-функції в Supabase, і кожна дія лишає запис в `audit_log`._

## Головні правила

1. **Спершу — запит.** Втручаєтеся в дані закладу лише на його запит: дзвінок, лист, Telegram. Запишіть, хто і коли попросив.
2. **Причина обов'язкова.** Функції підтримки не спрацюють без причини, мінімум 5 символів. Наприклад: «Тікет 12: власник просить скасувати подвійний штамп, Telegram 05.10».
3. **Менше даних — краще.** Шукайте заклад за `slug` або email власника. Без потреби не відкривайте списки клієнтів і не копіюйте телефони в чати.
4. **Не входьте як власник** і не генеруйте посилання для входу в чужий акаунт. Якщо власник не може увійти, допоможіть йому отримати лист (див. нижче).
5. **Усе, що змінює дані, — лише через функції `support_*`.** Прямі `update` / `delete` по таблицях заборонені. Виняток — зміна тарифу.

## Де працювати

Supabase → проєкт **production** → **SQL Editor**. Він працює з правами адміністратора, тож будьте уважні з вибором проєкту.

Логи: Vercel → проєкт → **Logs**. Події — це рядки JSON, фільтруйте за `"event":"…"` і `"businessId":"…"`. Персональні дані в логах маскуються автоматично (`[phone]`, `[email]`, `[token]`).

## 1. Знайти заклад

```sql
-- За адресою сторінки (slug) або назвою
select b.id, b.name, b.slug, b.plan, b.trial_ends_at, b.billing_status, u.email as owner_email
from businesses b join auth.users u on u.id = b.owner_id
where b.slug = 'barber-rivne' or b.name ilike '%барбер%';
```

Перед будь-яким подальшим кроком запишіть, що ви відкрили дані закладу:

```sql
select support_log('<business_id>', '<ваше імʼя>', 'looked_up_business', 'Тікет 12: не ставиться штамп');
```

## 2. Перевірити помилку

**Логи (Vercel):** фільтр `"businessId":"<business_id>"`. Події, які стосуються пілоту:

| Подія | Що означає |
|---|---|
| `stamp_added` / `stamp_rejected` (`reason`: `cooldown`, `not_found`, `inactive`, `staff_inactive`) | Штамп поставлено / відхилено, з причиною |
| `reward_redeemed` / `reward_rejected` | Винагороду видано / відхилено |
| `staff_login_failed` / `staff_login_locked` | Невдалий вхід у сканер / блокування після підбору |
| `card_issued` / `card_join_rejected` / `card_issue_failed` | Клієнт отримав картку / відмова (ліміт, частота) / помилка |
| `broadcast_sent` / `broadcast_failed`, `reminders_run` / `reminders_failed` | Розсилки й нагадування |
| `wallet_task_failed`, `wallet_save_failed` | Google Wallet |
| `request_error` | Будь-яка неочікувана помилка сервера (з `route` і `digest`) |

**Журнал штампів закладу** (те саме бачить власник на сторінці «Працівники»):

```sql
select e.created_at, e.type, s.name as staff, e.card_id
from stamp_events e left join staff s on s.id = e.staff_id
where e.business_id = '<business_id>'
order by e.created_at desc limit 30;
```

## 3. Типові звернення

### Подвійний / помилковий штамп

Скасувати можна лише **останню** подію картки, лише якщо це штамп і він не старший за 48 годин. Якщо цей штамп заповнив картку, винагорода теж забирається. Вже видану винагороду функція не чіпає.

```sql
select support_undo_last_stamp('<card_id>', '<ваше імʼя>', 'Тікет 7: працівник двічі натиснув +1');
```

Що поверне функція:
- `ok` — штамп скасовано;
- `last_event_not_a_stamp` — остання подія картки не штамп;
- `too_old` — штампу більше 48 годин;
- `reward_already_redeemed` — винагороду вже видано;
- `not_found` — картки немає.

У всіх випадках, крім `ok`, нічого не змінюється: домовтеся із закладом вручну.

`card_id` візьміть із журналу штампів вище, з часу й імені працівника. Код картки (QR-токен) у підтримці не потрібен і не запитується.

### Працівник забув PIN / пішов працівник

Це робить **власник** у кабінеті: «Працівники» → «Змінити PIN». Після зміни всі, хто увійшов зі старим PIN, одразу виходять. Підтримка PIN не бачить і не змінює.

### Сканер заблоковано («Забагато невдалих спроб»)

Блокування само знімається через 15 хвилин. Працівники, які вже увійшли, працюють далі. Якщо таке трапляється часто, хтось підбирає PIN: порадьте власнику змінити PIN на 6-значний.

### Власник не отримує лист для входу

1. Перевірте спам і правильність email.
2. Supabase → Authentication → Logs: чи відправлено лист.
3. Якщо вичерпано ліміт пошти, потрібен власний SMTP (`production-checklist.md`).

### Клієнт просить видалити свої дані

- **Власник** робить це сам: «Клієнти» → «Видалити дані».
- **Якщо клієнт звернувся напряму до нас:**

```sql
-- Знайти клієнта в закладі (за телефоном, який назвав клієнт)
select cu.id, cu.created_at from customers cu
where cu.business_id = '<business_id>' and cu.phone like '%501112233';

select support_anonymize_customer('<customer_id>', '<ваше імʼя>', 'Лист клієнта від 05.10: видалити дані');
```

Стираються ім'я, телефон і згода, стара картка перестає відкриватися, історія візитів лишається без імені.

### Підключити оплачений тариф (оплата за рахунком)

Це єдина пряма зміна таблиці. Спершу запишіть її в журнал:

```sql
select support_log('<business_id>', '<ваше імʼя>', 'plan_changed', 'Рахунок №3 оплачено 05.10, Плюс на 1 міс', '{"plan":"plus"}');
update businesses set plan = 'plus', billing_status = 'active', plan_renews_at = now() + interval '1 month'
where id = '<business_id>';
```

## 4. Журнал дій

```sql
-- Усе, що підтримка й власник робили з даними закладу
select created_at, actor_type, actor, action, target_type, target_id, reason, details
from audit_log where business_id = '<business_id>' order by created_at desc;
```

Власник бачить записи свого закладу (RLS), але не може їх змінити чи додати.
