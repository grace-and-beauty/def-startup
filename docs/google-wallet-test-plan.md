# Google Wallet: план тестування перед запуском

_Складено: 5 жовтня 2026, гілка `pilot-readiness`._

> **Статус:** код інтеграції Google Wallet написаний і покритий unit-тестами з **підробленими** відповідями Google (`tests/unit/wallet.test.ts`). Він **жодного разу не працював з реальним issuer-акаунтом і реальним Android-телефоном.** До проходження цього плану Google Wallet у продакшні **не вмикати** (див. `docs/production-checklist.md` §14). Нижче в розділі «Знахідки аудиту коду» — проблеми, які варто виправити до або під час тестування.

## 0. Як це влаштовано (коротко)

| Що | Де в коді | Що робить |
|---|---|---|
| Вибір провайдера | `src/lib/wallet/index.ts` → `getWalletProvider()` | Якщо задані **всі три** `GOOGLE_WALLET_*` → Google; інакше → `noopWalletProvider` (нічого не робить, кнопка прихована) |
| Payload-и | `src/lib/wallet/google-payload.ts` | Клас картки (`LoyaltyClass`, один на програму закладу), об'єкт (`LoyaltyObject`, один на картку клієнта), повідомлення, підписаний JWT |
| Виклики Google | `src/lib/wallet/google.ts` → `GoogleWalletProvider` | REST-запити до Wallet Objects API з токеном сервісного акаунта, тайм-аут 8 с на запит |
| Кнопка «Додати в Google Wallet» | `src/app/api/wallet/google/[token]/route.ts` | Оновлює/створює клас → підписує JWT з об'єктом картки → редирект на `pay.google.com/gp/v/save/<jwt>`; при помилці — назад на веб-картку з `?wallet=error` |
| Після штампа / видачі винагороди | `src/app/scan/[slug]/actions.ts` → `syncWalletCard()` | Якщо `cards.wallet_type = 'google'` — у фоні (`after()`) PATCH лічильників на об'єкті |
| Розсилка («всім» і «під ризиком») | `src/app/dashboard/(app)/messages/actions.ts` → `sendBroadcast()` | У фоні: бере отримувачів розсилки з бази (`listGoogleRecipientCardIds`, лише картки з `wallet_type = 'google'`) і робить `addMessage` на **кожен об'єкт** окремо, пачками по 5 |
| Нагадування (cron) | `src/lib/jobs/reminders.ts` → `runReminders()` | Після запису нагадування в базу — `addMessage` на кожен Google-об'єкт, пачками по 5 |

> **Згода на повідомлення.** Повідомлення закладу (розсилки, нагадування) отримують лише клієнти, які дали згоду (галочка при реєстрації картки або перемикач на веб-картці). Тому розсилка «всім» іде по одному об'єкту на кожного згодного клієнта, а не на клас; метод `broadcast()` (повідомлення на клас) видалено з провайдера. Структуроване логування — §6.

Ідентифікатори:
- клас: `<ISSUER_ID>.prog_<uuid програми>`
- об'єкт (картка): `<ISSUER_ID>.card_<uuid картки>`
- повідомлення: `msg_<uuid розсилки>` (розсилки), `rem_<uuid нагадування>` (нагадування)

Вони **детерміновані**: та сама картка завжди має той самий id пасу.

## 1. Налаштування Google (один раз)

### 1.1 Google Cloud
1. [console.cloud.google.com](https://console.cloud.google.com) → створи проєкт (напр. `loyalty-wallet`).
2. **APIs & Services → Library** → знайди **Google Wallet API** → **Enable**.
3. **IAM & Admin → Service Accounts → Create service account**: назва напр. `wallet-prod`. Ролі в Google Cloud **не потрібні** (доступ дається в Wallet Console, крок 1.2).
4. Відкрий створений акаунт → **Keys → Add key → Create new key → JSON** → файл завантажиться. У ньому потрібні два поля: `client_email` і `private_key`.
   - Зберігай файл у менеджері паролів, видали з «Завантажень». Не клади в репозиторій.
   - Для тестування зроби **окремий** сервісний акаунт (`wallet-test`) зі своїм ключем.

### 1.2 Google Pay & Wallet Console
1. [pay.google.com/business/console](https://pay.google.com/business/console) → увійди тим Google-акаунтом, який буде власником бізнесу.
2. Заповни профіль бізнесу → розділ **Google Wallet API** → створи **Issuer account**. Скопіюй **Issuer ID** (довге число) → це `GOOGLE_WALLET_ISSUER_ID`.
3. **Users** (Користувачі) → **Invite a user** → email сервісного акаунта (`client_email` з JSON) → рівень доступу **Developer** (достатньо для створення класів/об'єктів). Повтори для тестового сервісного акаунта.
4. Там же додай **тестові Google-акаунти** людей, які тестуватимуть на телефонах (див. §3).
5. Поки акаунт у **demo mode** — нічого не публікуй. Коли тест-план пройдено: **Google Wallet API → Request publishing access** (Google перевіряє профіль і вигляд картки; може зайняти кілька днів). Вимоги до картки (логотип, назва) перевір у консолі під час запиту.

## 2. Змінні середовища

| Змінна | Значення | Формат |
|---|---|---|
| `GOOGLE_WALLET_ISSUER_ID` | Issuer ID з Pay & Wallet Console | лише цифри, напр. `3388000000012345678` |
| `GOOGLE_WALLET_SERVICE_ACCOUNT_EMAIL` | `client_email` з JSON-ключа | `wallet-prod@<project>.iam.gserviceaccount.com` |
| `GOOGLE_WALLET_PRIVATE_KEY` | `private_key` з JSON-ключа | один рядок, переноси як `\n` (див. нижче) |
| `NEXT_PUBLIC_SITE_URL` | **публічна `https://` адреса** сайту | без `/` в кінці |

**`GOOGLE_WALLET_PRIVATE_KEY`** — візьми значення поля `private_key` **як є** з JSON-файлу (воно вже містить `\n` замість переносів):
```bash
# macOS: скопіювати ключ у буфер обміну з JSON-файлу (потрібен jq: brew install jq)
jq -r '.private_key' ~/Downloads/<файл-ключа>.json | awk '{printf "%s\\n", $0}' | sed 's/\\n$//' | pbcopy
```
Встав у Vercel **без лапок**. Має починатися з `-----BEGIN PRIVATE KEY-----\n` і закінчуватися `-----END PRIVATE KEY-----` (з `\n` або без в кінці). Код замінює `\n` на справжні переноси (`googleWalletEnv()` у `src/lib/env.ts`). Справжні переноси рядків у полі Vercel теж спрацюють.

**`NEXT_PUBLIC_SITE_URL` має бути публічним `https`**, бо:
- Google завантажує з нього запасний логотип `/wallet-logo.png` (коли в закладу немає свого) — `localhost` Google не бачить;
- на пасі є посилання «Веб-картка» на `<SITE_URL>/card/<token>`;
- в JWT передається `origins: [<SITE_URL>]`.

Якщо адреса не `https://`, Wallet автоматично вимикається (noop) і в лог пишеться попередження (виправлено W-04).

Після зміни змінних — **Redeploy** у Vercel.

## 3. Demo mode vs live mode

| | Demo mode (до схвалення) | Live (після publishing access) |
|---|---|---|
| Хто може зберегти картку | **лише** Google-акаунти, додані в Pay & Wallet Console (Users / test accounts) | будь-хто |
| Вигляд | на картці позначка на кшталт «TEST ONLY» | звичайна |
| Що побачить сторонній клієнт | помилку на сторінці Google при збереженні | — |

Тому в Production **не вмикай** Wallet до схвалення: реальні клієнти побачать кнопку, натиснуть — і отримають помилку від Google.

## 4. Підготовка тестового телефона

1. Android-телефон (Android 9+ рекомендовано), встановлено **Google Wallet** з Play Store.
2. На телефоні — увійти в **той Google-акаунт, який додано тестовим** у Pay & Wallet Console.
3. Перевір, що Google Wallet відкривається і працює в країні цього акаунта (якщо застосунок пише, що недоступний у регіоні — тест на цьому акаунті неможливий).
4. Сповіщення від Google Wallet увімкнені (Налаштування → Застосунки → Google Wallet → Сповіщення).
5. Середовище для тесту: Preview-деплой або окремий тестовий деплой з **тестовим** Supabase і **тестовим** сервісним акаунтом, з публічним `https`. Локальний `localhost` не підходить (див. §2). Тунель `cloudflared` теж можливий, але його адреса має бути в `NEXT_PUBLIC_SITE_URL`.
6. У тестовому закладі вимкни або зменш кулдаун, щоб не чекати 10 хв між штампами: `STAMP_COOLDOWN_MINUTES=0` **лише на тестовому деплої**.
7. Тариф тестового закладу — тріал Плюс (для розсилки «під ризиком» і нагадувань потрібні функції Плюс).

### Допоміжні інструменти для перевірки (необов'язково, для інженера)

Знайти картку в базі (SQL Editor тестового проєкту):
```sql
select id, qr_token, wallet_type, google_object_id, stamps_count, rewards_available
from public.cards where qr_token = '<токен з адреси /card/...>';
```

Подивитися, що реально лежить у Google (потрібен `gcloud`, ключ тестового сервісного акаунта):
```bash
gcloud auth activate-service-account --key-file=<тестовий-ключ>.json
TOKEN=$(gcloud auth print-access-token --scopes=https://www.googleapis.com/auth/wallet_object.issuer)
ISSUER=<GOOGLE_WALLET_ISSUER_ID>

# об'єкт картки
curl -s -H "Authorization: Bearer $TOKEN" \
  "https://walletobjects.googleapis.com/walletobjects/v1/loyaltyObject/$ISSUER.card_<uuid картки>" | jq '{state, loyaltyPoints, secondaryLoyaltyPoints, messages}'

# клас програми
curl -s -H "Authorization: Bearer $TOKEN" \
  "https://walletobjects.googleapis.com/walletobjects/v1/loyaltyClass/$ISSUER.prog_<uuid програми>" | jq '{reviewStatus, programName, hexBackgroundColor, messages}'
```

Логи: Vercel → проєкт → **Logs**, фільтр за текстом `wallet` (див. §6).

## 5. Тест-кейси

Позначки: ✅ пройдено, ❌ не пройдено (записати, що побачили, і рядок з логів).

### T1. Кнопка вимкнена без ключів (noop)
- **Кроки:** деплой без `GOOGLE_WALLET_*` → відкрий `/c/<slug>` і `/card/<token>`; в кабінеті — сторінка «Розсилки».
- **Очікується:** кнопки «Додати в Google Wallet» немає; на сторінці розсилок напис «Google Wallet не підключено: повідомлення буде видно на веб-картці»; ручний перехід на `/api/wallet/google/<token>` повертає на веб-картку без помилки; штампи й розсилки працюють, у логах немає `wallet ... failed`.

### T2. Створення і збереження картки
- **Кроки:** деплой з тестовими ключами → новий клієнт на `/c/<slug>` → «Додати в Google Wallet» на телефоні.
- **Очікується:**
  - відкривається сторінка Google зі сповіщенням про збереження картки → «Зберегти» → картка в Google Wallet;
  - на картці: логотип закладу (або нейтральний), колір фону закладу, назва закладу, «Штампи 0 / N», «Подарунки 0», QR-код, ім'я клієнта (або назва закладу, якщо ім'я не вказане);
  - у деталях картки: «Винагорода — Кожен N-й візит: …», «Умови» (якщо задані), посилання «Веб-картка» відкриває `/card/<token>`;
  - у базі: `cards.wallet_type = 'google'`, `google_object_id = '<ISSUER>.card_<uuid>'`; `programs.google_class_id` заповнений;
  - у логах **немає** події `wallet_save_failed`.
- **Додатково перевірити:** довжину посилання на збереження (див. W-03):
  ```bash
  curl -s -o /dev/null -w "%{redirect_url}\n" https://<тестовий-домен>/api/wallet/google/<token> | wc -c
  ```
  Записати число. Якщо Google показує помилку при збереженні, а довжина близька до 2000+ символів — це W-03.

### T3. QR з Google Wallet сканується
- **Кроки:** працівник у `/scan/<slug>` сканує QR з картки в Google Wallet (не з веб-картки).
- **Очікується:** знаходиться та сама картка клієнта, що й з веб-картки.

### T4. Повторне збереження (ідемпотентність)
- **Кроки:** ще раз натиснути «Додати в Google Wallet» для тієї ж картки (той самий телефон); потім — з другого тестового акаунта.
- **Очікується:** Google показує, що картка вже збережена / зберігає ту саму картку; **дублікатів у Wallet немає**; у Google один об'єкт з тим самим id; помилок у логах немає.

### T5. Штамп оновлює картку в Wallet
- **Кроки:** +1 штамп у сканері.
- **Очікується:** протягом ~1 хв (зазвичай секунди) на картці в Wallet «Штампи 1 / N». Через curl з §4 — `loyaltyPoints.balance.string = "1 / N"`. У логах немає `wallet_task_failed` з `task: "updateCard"`.
- **Повторити** кілька штампів поспіль (з кулдауном 0) — кінцеве значення в Wallet має збігатися з веб-карткою (див. W-09).

### T6. Стан винагороди
- **Кроки:** доставити штампи до N.
- **Очікується:** «Штампи 0 / N» (лічильник обнуляється), «Подарунки 1». Потім «Видати винагороду» в сканері → «Подарунки 0». Кожна зміна з'являється в Wallet.
- **Зауваження:** окремого візуального стану «винагорода готова» (інший колір / банер) у коді немає — лише число «Подарунки». Погодь, чи цього достатньо.

### T7. Штамп для картки, яку клієнт не зберіг
- **Кроки:** клієнт натиснув «Додати в Google Wallet», але на сторінці Google **закрив**, не зберігши. Поставити штамп.
- **Очікується:** штамп проходить нормально; Google відповідає 404 — це не вважається помилкою, у логах нічого. (Зверни увагу: у базі така картка вже позначена `wallet_type = 'google'` — див. W-05.)

### T8. Розсилка «всім»
- **Підготовка:** два тестові клієнти з картками в Google Wallet: клієнт А **дав згоду** на повідомлення (на веб-картці), клієнт Б — **ні**.
- **Кроки:** кабінет → Розсилки → текст → «Усім» → Надіслати.
- **Очікується:** у клієнта А — сповіщення від Google Wallet з назвою закладу і текстом, повідомлення в деталях картки і на веб-картці. У клієнта Б — **нічого** (ні в Wallet, ні сповіщення). У Google (curl **об'єкта** А) — `messages[].id = "msg_<uuid>"`; на **класі** повідомлень немає. У логах немає `wallet_task_failed` з `task: "messageCards"`.
- **Додатково:** зроби 3–4 розсилки за день. Записати, скільки дійшло сповіщенням, а скільки лише з'явилось на картці (Google обмежує кількість сповіщень на картку за добу — перевір актуальний ліміт у документації). Перевір, чи старі повідомлення накопичуються на картці (див. W-07).

### T9. Розсилка «під ризиком»
- **Підготовка:** клієнт з Google-карткою і згодою на повідомлення, який давно не приходив (на тестовому проєкті можна змінити `last_visit_at` / події штампів SQL-запитом, щоб він потрапив у «під ризиком»), і ще один клієнт у Wallet, який **не** під ризиком.
- **Кроки:** Розсилки → «Клієнтам під ризиком» → Надіслати.
- **Очікується:** сповіщення **лише** на картці клієнта під ризиком, у другого — нічого. У Google — повідомлення на об'єкті (`loyaltyObject`), не на класі. У логах немає `wallet_task_failed` з `task: "messageCards"`.

### T10. Нагадування (cron)
- **Підготовка:** у програмі закладу увімкнені нагадування; клієнт з Google-карткою і згодою на повідомлення (перевір, чи нагадування в цій гілці теж фільтруються за згодою — додай другого клієнта без згоди і переконайся, що він нічого не отримав), останній візит давніше за налаштовану кількість днів, після останнього візиту нагадувань не було.
- **Кроки:**
  ```bash
  curl -s -H "Authorization: Bearer <CRON_SECRET тестового деплою>" https://<тестовий-домен>/api/cron/reminders
  ```
- **Очікується:** відповідь `{"ok":true, ..., "reminded":1, "walletSent":1, "walletFailed":0}`; на телефоні сповіщення з текстом нагадування; на веб-картці воно ж.
- **Повторний виклик** того ж дня: `reminded: 0`, `walletSent: 0` — дубля немає.

### T11. Зміна дизайну / правил програми
- **Кроки:** у налаштуваннях змінити колір, логотип або текст винагороди.
- **Очікується за поточним кодом:** **збережені картки не оновлюються**, доки хтось із клієнтів знову не натисне «Додати в Google Wallet» (тоді клас оновлюється для всіх). Записати фактичну поведінку — див. W-06.

### T12. Неактивний заклад
- **Кроки:** перевести тестовий заклад у неактивний стан (закінчений тариф) → натиснути «Додати в Google Wallet».
- **Очікується:** редирект на веб-картку без збереження; нових пасів не видається.

### T13. Помилкові ключі (обробка помилок)
- **Кроки:** на тестовому деплої задати неправильний `GOOGLE_WALLET_PRIVATE_KEY` (напр. обрізаний) → Redeploy → натиснути кнопку; поставити штамп картці, яка вже в Wallet.
- **Очікується:** кнопка повертає на веб-картку з повідомленням «Не вдалося відкрити Google Wallet. Спробуйте ще раз пізніше — веб-картка працює.»; у логах подія `wallet_save_failed`; штамп **проходить**, у логах `wallet_task_failed` з `task: "updateCard"`. Жодна основна операція не ламається.

### T14. Ліміт частоти
- **Кроки:** 11 разів за хвилину натиснути кнопку з одного телефона.
- **Очікується:** 11-й раз — повернення на веб-картку з помилкою (ліміт 10/хв на IP на заклад, `WALLET_SAVE_RATE_LIMIT`).

## 6. Де логуються помилки сьогодні

У цій же гілці логування переводиться на структуровані події: `logEvent(level, event, fields)` з `src/lib/log.ts` пише один JSON-рядок на подію (видно у Vercel → Logs, шукати за `event`). Сповіщень про помилки (Sentry / log drain) у коді поки немає. Стан на момент написання (код ще змінюється — звір перед тестом):

| Подія (`event`) | Поля | Де | Коли |
|---|---|---|---|

## 7. Безпечні повтори (чи можна повторити дію)

| Дія | Ідемпотентна? | Пояснення |
|---|---|---|
| Збереження картки (`getSaveUrl`) | **Так** | Id об'єкта детермінований (`<ISSUER>.card_<uuid>`). Повторне збереження не створює дубль. |
| Створення/оновлення класу (`upsertClass`) | **Так** | PATCH; якщо 404 — POST; 409 («вже створено паралельно») вважається успіхом. |
| Оновлення лічильників (`updateCard`) | **Так** | PATCH з абсолютними значеннями («3 / 6», а не «+1»). Повтор дає той самий результат. |
| Повідомлення (`messageCard`; `broadcast` зараз не викликається) | **Не перевірено** | Id повідомлення стабільний (`msg_…`, `rem_…`), і коментар у `types.ts:21` стверджує, що повтор не дублює. Але як Google відповідає на повторний `addMessage` з тим самим id (ігнорує / 409 / дубль) — **не перевірялось**. Якщо 409 — код вважатиме це помилкою (див. W-08). |

**Автоматичних повторів у коді немає.** Якщо Google тимчасово недоступний, оновлення / повідомлення просто губиться (запис у лозі). Лічильники відновляться при наступному штампі цієї картки; повідомлення і нагадування — ні (див. W-02).

Ручний повтор на сьогодні:
- лічильники — наступний штамп або повторне «Додати в Google Wallet» (оновлює клас, але **не** лічильники існуючого об'єкта);
- повідомлення — лише нова розсилка (витрачає місячну квоту закладу).

## 8. Як швидко вимкнути Wallet у продакшні і відкотитись

**Перевірено в коді:** `googleWalletEnv()` (`src/lib/env.ts:83-89`) повертає `null`, якщо **хоча б одна** з трьох змінних порожня або з самих пробілів → `getWalletProvider()` (`src/lib/wallet/index.ts:23-32`) віддає `noopWalletProvider`. Наслідки:
- кнопка ховається на `/card/[token]` і `/c/[slug]` (`isGoogleWalletConfigured()`);
- `/api/wallet/google/<token>` одразу повертає на веб-картку (`route.ts:30`);
- `scheduleWalletTask()` нічого не запускає (`background.ts:13`), `runWalletTask()` повертає успіх без дій;
- cron пропускає Wallet (`reminders.ts:68`, `wallet.isConfigured()`);
- сторінка розсилок показує «Google Wallet не підключено…».

**Кроки:**
1. Vercel → Settings → Environment Variables → Production → очистити `GOOGLE_WALLET_ISSUER_ID` (значення можна зберегти в менеджері паролів).
2. Deployments → останній → ⋯ → **Redeploy**.
3. Перевір: на будь-якій веб-картці кнопки немає.

Наслідки для клієнтів: вже збережені картки лишаються в їхньому Google Wallet, QR на них продовжує скануватись (той самий токен), але лічильники й повідомлення більше не оновлюються, доки Wallet не ввімкнуть знову. Дані в базі не змінюються (`wallet_type = 'google'` залишається), тож повторне ввімкнення продовжить оновлення тих самих карток.

Альтернатива при проблемі в новому коді — Instant Rollback деплою (Vercel → Deployments → Promote попередній).

**Якщо витік ключ:** Google Cloud → IAM → Service Accounts → акаунт → Keys → видалити ключ → створити новий → оновити `GOOGLE_WALLET_PRIVATE_KEY` → Redeploy.
