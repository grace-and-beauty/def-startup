# План реалізації MVP

> Що будуємо — `prd.md`. Як влаштовано — `architecture.md`.
> 4 етапи, кожен закінчується **робочою збіркою** і комітом. Наступний етап починається лише після того, як перевірки попереднього зелені.

## Загальні правила

- Мова коду — англійська (імена, коментарі); тексти інтерфейсу — українська через `t()`.
- Перед завершенням кожного етапу обовʼязково: `npm run typecheck`, `npm run lint`, `npm run build` — без помилок. З етапу 4 — ще `npm test`.
- Секрети не комітити. Нові змінні — одразу в `.env.example` з коментарем.
- Назву і дизайн не вигадувати (`architecture.md` → §9).
- Якщо зовнішній сервіс недоступний (Google Wallet, Supabase cloud) — код працює з `noop` / локальною БД, а в README описано, що налаштувати вручну.
- Коміт після кожного логічного кроку; повідомлення англійською, у форматі `stage-N: …`.

## Етап 1 — Каркас і дані

**Мета:** проєкт запускається, схема БД з RLS готова, є типізований доступ до даних і конфіги.

1. Next.js (App Router, TypeScript strict, `src/`, ESLint), Tailwind, shadcn/ui (базові компоненти: button, input, label, card, dialog, table, tabs, badge, toast/sonner, form).
2. Скрипти `package.json`: `dev`, `build`, `start`, `lint`, `typecheck`, `test`, `test:unit`, `test:integration`, `test:e2e`, `db:test:up` / `db:test:down`.
3. `src/config/brand.ts`, `niches.ts` (8 ніш з `architecture.md`/PRD: avtomyika, barbershop, kavyarnia, manikur, gruming, avtoservis, pekarnia, kvitkovyi — з `stamps_required`, `reward_text`, `reminder_days`, `reminder_text`, кольорами, текстами для посадкової), `plans.ts`.
4. Дизайн-токени в `globals.css` (нейтральні), i18n-хелпер `t()` + `uk.json`.
5. Supabase-клієнти: `server.ts` (`@supabase/ssr`), `browser.ts`, `admin.ts` (`server-only`).
6. **Міграції** `supabase/migrations/`: усі таблиці §4.1, індекси, `is_business_owner`, RLS-політики §4.2, тригер `protect_billing_fields`, тригер `updated_at`, RPC `apply_stamp` / `redeem_reward` (транзакційні, `for update`), RPC аналітики (§5.5).
7. `supabase/seed.sql`: демо-заклад «Автомийка Демо» з програмою, працівником (PIN `1234`), 40 клієнтами і ~300 подіями за 60 днів (для аналітики).
8. TS-типи БД (`src/lib/data/types.ts` — вручну або згенеровані) і модулі `src/lib/data/*` (businesses, programs, staff, customers, cards, events, messages).
9. `.env.example`, `README.md` (запуск, міграції, env).

**Готово, коли:** `typecheck` / `lint` / `build` зелені; міграції застосовуються на чистий Postgres без помилок (локальний Supabase через `supabase start`, або Docker `postgres:16` зі стабом схеми `auth` — `auth.users`, `auth.uid()` — для тестів).

## Етап 2 — Екрани

**Мета:** усі сторінки існують, мобільні, нейтральні, підключені до даних через Server Actions (логіку можна викликати з простих реалізацій; повна логіка — етап 3).

Публічні:
1. `/` — заголовок + плитки ніш з `niches.ts`; `/dlya/[niche]` — болі, приклад картки (компонент `CardPreview`), CTA; `/pricing` — 3 тарифи з `plans.ts`.
2. `/login` (magic link), `/auth/callback`.
3. `/c/[slug]` — превʼю картки закладу, форма (імʼя, телефон), кнопки «Додати в Google Wallet» (якщо провайдер налаштований) і «Відкрити веб-картку».
4. `/card/[token]` — веб-картка: назва/логотип/кольори закладу, `StampProgress` (кружечки N з M), QR (`qrcode`), винагороди до видачі, останнє повідомлення закладу, підказка «Додайте на головний екран».

Працівник:
5. `/scan/[slug]` — екран PIN → сканер (`@zxing/browser`), ручний ввід коду, картка клієнта, кнопки «+1 штамп» / «Видати винагороду», великий екран-підтвердження (зелений / червоний з причиною).

Власник (`/dashboard`, layout з перевіркою сесії і нижнім меню на мобільному):
6. `onboarding` — майстер 5 кроків: ніша → назва + slug → логотип + кольори (живе превʼю) → правило (штампів, винагорода) → PIN «Загальний» → фінал з посиланням на постер. Поки `onboarding_done=false` — редірект сюди.
7. Головна — картки цифр (видано карток, штампів за місяць, повернення, ↑↓ до минулого місяця), банер тріалу.
8. `analytics` — графіки й метрики §5.5 з підказками й кнопками дій; на Базовій — **розмите превʼю** + CTA «Відкрити в тарифі Плюс».
9. `clients` — таблиця (імʼя, телефон, штампи, візити, останній візит), пошук.
10. `messages` — форма (лічильник символів, залишок розсилок за тарифом) + історія.
11. `staff` — список, додати/деактивувати, змінити PIN (окремі PIN — лише Плюс; на Базовій — лише «Загальний»).
12. `poster` — сторінка A5 для друку (`@media print`): логотип, «Збирай штампи — N-та в подарунок», QR на `/c/[slug]`, кнопка «Друкувати / Зберегти PDF».
13. `settings` — дизайн картки, правило, тексти, нагадування (днів, текст, увімкнути), середній чек.
14. `billing` — поточний (ефективний) тариф, тріал до…, ліміти та використання, порівняння тарифів, «Звʼязатися для оплати» (MVP без онлайн-оплати).

**Готово, коли:** усі маршрути рендеряться на демо-даних seed; навігація працює; `typecheck` / `lint` / `build` зелені.

## Етап 3 — Логіка

**Мета:** усе з PRD §7 «Входить» працює по-справжньому і безпечно.

1. `domain/stamps.ts` — `applyStamp`, `redeemReward`, кулдаун, переповнення → винагорода; Server Actions викликають RPC `apply_stamp` / `redeem_reward`.
2. `auth/staff-session.ts` + `security/pin.ts` + `security/rate-limit.ts` — вхід по PIN, блокування спроб, перевірка належності картки закладу на кожній дії.
3. `security/tokens.ts` — генерація `qr_token`; slug-валідація й унікальність (`domain/slug.ts`, транслітерація кирилиці).
4. `domain/plans.ts` — `effectivePlan`, `hasFeature`, `getLimit` (§6.2); застосувати в усіх Server Actions (ліміт клієнтів у `joinProgram`, розсилки, працівники, аналітика, нагадування) і в UI.
5. `wallet/` — інтерфейс, `google.ts` (class/object upsert, JWT save-лінк, update, messages), `noop.ts`, вибір провайдера за env; чисті білдери payload.
6. Розсилки (`target: all | at_risk`), запис у `messages`, показ останнього повідомлення на веб-картці.
7. `domain/analytics.ts` — похідні метрики й підказки (§5.5) поверх RPC.
8. `domain/reminders.ts` + `/api/cron/reminders` (CRON_SECRET) + `vercel.json`.
9. Онбординг створює business + program + staff «Загальний» атомарно; логотип у Storage з перевірками (§8).
10. Заклад `inactive` → `/c/[slug]` не видає нових карток; поведінка за §6.2.
11. Заголовки безпеки в `next.config`.

**Готово, коли:** повний сценарій вручну на локальній БД: онбординг → постер → приєднання → 6 штампів (з кулдауном, змоканим у тестовому режимі через `STAMP_COOLDOWN_MINUTES=0`) → винагорода → розсилка → аналітика; `typecheck` / `lint` / `build` зелені.

## Етап 4 — Тести

**Мета:** ключова логіка і доступи покриті автотестами; усі тести зелені.

1. **Unit (Vitest)** — без мережі й БД:
   - `stamps`: звичайний штамп, кулдаун, заповнення → винагорода, видача без винагород → помилка, межі 2/20;
   - `plans`: тріал активний/закінчився, past_due + grace, canceled → basic → inactive, `hasFeature`, ліміти;
   - `analytics`: повернення, медіанний інтервал, на ризику, ефект розсилки, порівняння місяців, часові пояси;
   - `reminders`: вибір карток (межі днів, вже нагадано);
   - `wallet/google` білдери payload і JWT (з тестовим ключем);
   - `security`: токени (довжина/алфавіт/унікальність), PIN-хеш, staff-сесія (підпис, прострочення, підміна), slug.
2. **Integration (Vitest + Postgres у Docker)** — міграції на чисту БД:
   - RLS: власник A **не бачить і не змінює** дані закладу B (усі таблиці); anon не читає нічого;
   - тригер: власник не може змінити `plan` / `trial_ends_at`;
   - RPC `apply_stamp` / `redeem_reward`: коректні лічильники, паралельні виклики не дублюють штамп;
   - RPC аналітики на seed-даних повертають очікувані агрегати.
3. **E2E (Playwright, smoke)** — головна, сторінка ніші, тарифи, логін рендеряться; якщо доступний локальний Supabase — сценарій «приєднання → веб-картка → сканер (PIN) → штамп».
4. Виправити всі знайдені баги; задокументувати в README, як запускати кожен тип тестів.

**Готово, коли:** `npm test` (unit + integration) зелений; e2e smoke зелений; `typecheck` / `lint` / `build` зелені; README оновлено.
