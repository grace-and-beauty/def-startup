## Перевірено, проблем немає

- Ізоляція закладів: RLS на всіх таблицях, композитні FK `(id, business_id)`, RPC з явним `business_id`; `pin_hash` недоступний власнику для читання.
- Поля тарифу захищені тригером + тепер і грантами.
- Ін'єкції: SQL лише параметризований (PostgREST / RPC), немає shell, `eval`, шляхів з вводу; єдиний `dangerouslySetInnerHTML` — SVG з бібліотеки `qrcode` з нашого значення.
- Завантаження логотипа: тип за magic bytes, ≤ 1 МБ, випадкове ім'я в теці закладу; видалення не виходить за теку.
- Редирект після входу (`safeNextPath`) — лише відносні шляхи цього сайту.
- Гонки: штампи, винагороди, ліміти клієнтів і розсилок — під row lock / advisory lock.
- Заголовки: CSP (`img-src` лише свій домен і Supabase), HSTS, `frame-ancestors 'none'`, Permissions-Policy.
- Cron: без `CRON_SECRET` закритий (503).

## Залишкові ризики — перевірити людині

- **IP за проксі.** Ліміти на IP беруть перше значення `x-forwarded-for`. На Vercel цей заголовок ставить сам Vercel; на іншому хостингу перевірити, що клієнт не може його підмінити. Ліміти «на заклад» від IP не залежать.
- **Блокування входу працівників зловмисником.** 30 невдалих спроб за 15 хв блокують нові входи в сканер закладу (наявні сесії працюють). Це свідомий компроміс проти брутфорсу.
- **CSP з `'unsafe-inline'` для скриптів** — вимога Next.js без nonce; React екранує весь вивід, тож ризик низький.
- **Демо-дані** (`supabase/seed.sql`, PIN `1234`) — лише для dev-проєкту; у продакшн seed не заливати.
- **Продакшн-проєкт Supabase** створити окремо з новим паролем БД (пароль dev-проєкту пересилався в чаті).
- Аналітика (функція тарифу Плюс) доступна власнику на Базовій через прямий виклик RPC — це його власні дані, лише обхід «розмитого превʼю».
